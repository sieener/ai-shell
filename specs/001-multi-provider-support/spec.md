# Feature Specification: Multi-Provider Support

**Feature Branch**: `001-multi-provider-support`
**Created**: 2026-01-29
**Status**: Draft
**Input**: User description: "Please help refactor the tool to accept the model-provider from gemini and local model (ollama)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Configure Gemini as Provider (Priority: P1)

As a user, I want to use Google's Gemini API instead of OpenAI so I can leverage
Google's models for shell command generation.

**Why this priority**: Gemini is a major cloud provider with wide availability
and competitive pricing. Adding Gemini support doubles the user's provider options.

**Independent Test**: User can set `PROVIDER=gemini` and `GEMINI_KEY`, then run
`ai "list files"` and receive a valid shell command generated by Gemini.

**Acceptance Scenarios**:

1. **Given** user has Gemini API key, **When** user runs
   `ai config set PROVIDER=gemini` and `ai config set GEMINI_KEY=<key>`,
   **Then** config file stores these values correctly.
2. **Given** provider is set to gemini with valid key, **When** user runs
   `ai "list all files"`, **Then** command is generated using Gemini API.
3. **Given** provider is set to gemini without key, **When** user runs `ai`,
   **Then** clear error message indicates missing GEMINI_KEY.

---

### User Story 2 - Configure Ollama as Provider (Priority: P2)

As a user, I want to use a local Ollama instance so I can generate commands
without internet access and keep my data private.

**Why this priority**: Local models are increasingly popular for privacy and
cost reasons. Ollama is the de-facto standard for local model serving.

**Independent Test**: User can set `PROVIDER=ollama` and optionally
`OLLAMA_HOST`, then run `ai "list files"` and receive a valid shell command
from the local Ollama instance.

**Acceptance Scenarios**:

1. **Given** Ollama is running locally, **When** user runs
   `ai config set PROVIDER=ollama`, **Then** subsequent commands use Ollama.
2. **Given** provider is ollama with default host, **When** user runs
   `ai "show disk usage"`, **Then** command is generated using local Ollama.
3. **Given** Ollama is not running, **When** user runs `ai`, **Then** clear
   error message indicates Ollama connection failure with remediation hint.
4. **Given** custom Ollama host, **When** user sets `OLLAMA_HOST=http://server:11434`,
   **Then** tool connects to that endpoint.

---

### User Story 3 - Seamless Provider Switching (Priority: P3)

As a user, I want to easily switch between providers so I can use different
models for different tasks or fallback when one provider is unavailable.

**Why this priority**: Flexibility is a key value proposition. Users should not
be locked into a single provider.

**Independent Test**: User can change `PROVIDER` setting and immediately use
a different provider without reconfiguring other settings.

**Acceptance Scenarios**:

1. **Given** both OpenAI and Gemini keys configured, **When** user changes
   `PROVIDER` value, **Then** next command uses the new provider.
2. **Given** config UI displayed, **When** user selects "Provider",
   **Then** list shows available providers (openai, gemini, ollama).
3. **Given** provider set to unknown value, **When** user runs `ai`,
   **Then** clear error lists valid provider options.

---

### Edge Cases

- What happens when API key is valid format but rejected by provider?
- **Resolved:** If Ollama model is missing, system logs a warning before the request proceeds (allowing the provider to return its own error).
- **Resolved:** If configured `MODEL` is incompatible with current `PROVIDER`, warn user and use provider's default model.
- How does streaming work if provider doesn't support it?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST support three providers: openai, gemini (default), ollama
- **FR-002**: System MUST store provider selection in config file as `PROVIDER`
- **FR-003**: System MUST support provider-specific API keys:
  - `OPENAI_KEY` for OpenAI
  - `GEMINI_KEY` for Gemini
  - No key required for Ollama (uses `OLLAMA_HOST`, default `http://localhost:11434`)
- **FR-004**: System MUST validate provider before making API calls
- **FR-005**: System MUST support provider-specific endpoints:
  - `OPENAI_API_ENDPOINT` for OpenAI
  - `GEMINI_API_ENDPOINT` for Gemini (optional)
  - `OLLAMA_HOST` for Ollama
- **FR-006**: System MUST support streaming responses for all providers that offer it
- **FR-007**: System MUST provide clear error messages specific to each provider
- **FR-008**: Config UI MUST allow selection of provider from dropdown
- **FR-009**: System MUST support provider-specific default models:
  - OpenAI: `gpt-4o-mini`
  - Gemini: `gemini-3-pro-preview`
  - Ollama: `qwen2.5-coder:14b`
- **FR-010**: System MUST log a warning if the configured Ollama model is not available locally before attempting the request.
- **FR-011**: System MUST warn and use provider default model if configured `MODEL` is incompatible with selected `PROVIDER`.

### Key Entities

- **Provider**: Enumeration of supported providers (openai, gemini, ollama)
- **ProviderConfig**: Provider-specific configuration (key, endpoint, model defaults)
- **CompletionClient**: Interface for making completion requests regardless of provider

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All three providers (OpenAI, Gemini, Ollama) can successfully generate
  shell commands
- **SC-002**: Switching providers via config requires only changing `PROVIDER` value
- **SC-003**: Error messages for each provider clearly identify the provider and
  suggest provider-specific remediation
- **SC-004**: Existing OpenAI users can continue using OpenAI by setting `PROVIDER=openai`
  (note: default provider is now Gemini for new installations)
